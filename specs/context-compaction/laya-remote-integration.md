# 별도 노드 Laya 연동 상태 (#19 Draft)

## 결론

브리지는 공식 Laya v0.3.21의 HTTP API를 호출하는 코드를 갖는다. 브리지에 Laya 모델이나 서버를 설치하지 않는다. **개발 머신에서 서버 접속과 단일 혼합 언어 선택 호출은 확인했지만, 결과 품질·운영 브리지 노드 접근은 검증하지 못했으므로 기본 설정에서는 호출하지 않는다.** 배포와 Tailscale 설정은 Atlas 담당이다.

## 동작 범위

- 기존 Foundry OpenAI Chat Completions **비스트리밍** 요청에 `x-hermes-conversation` 헤더가 있는 경우만 기존 축약 기능의 대상이다. 브리지가 원본 대화를 고치지 않는다.
- 주 LLM이 `hide_context`를 요청한 때에만 Laya가 **추가로 남길 원문 한 줄**을 고른다. 기존 규칙이 보호한 오류와 필수 증거는 Laya가 삭제할 수 없다. 원문 한 줄을 그대로 복사해 고정하며, 이후 요청마다 재생성하지 않는다.
- `list_context_items` 호출 때에만 Laya가 복원 후보의 표시 순서를 조정한다. 목록의 항목을 없애거나 자동으로 `unhide_context`를 실행하지 않는다. 최종 복원은 주 LLM이 결정한다.
- `model: multilingual`을 명시해 `POST /v1/systemone`으로 보낸다. 응답의 최상위 `model` 문자열은 실제 체크포인트가 아니므로 `routing.model == multilingual`을 확인한다. `max_len=8192`, `head_max_len=4096`이다. 앱 인증을 새로 추정하거나 OpenAI 채팅 API로 보내지 않는다.
- Laya에 보내는 내용은 현재 요청 일부와 길이를 제한한 원문 구간 또는 축약 항목의 짧은 발췌다. **이 내용에는 민감한 정보가 들어 있을 수 있다.** 비밀 삭제·권한 판단에 Laya를 사용하지 않는다. 서버가 요청 본문을 보관·기록하는지, Tailscale 정책이 브리지→Laya 트래픽만 허용하는지는 Atlas가 확인해야 한다.

## 설정과 안전한 기본값

`.env.example`을 참고한다. URL은 코드에 넣지 않고 배포 환경에서 주입한다.

| 환경 변수 | 기본값 | 목적 |
| --- | --- | --- |
| `LAYA_BASE_URL` | 빈 값 | `http://<Tailscale 주소>:8000` 형태의 **실제 서버 origin**. `/v1/systemone` 경로는 붙이지 않는다. |
| `CONTEXT_COMPACTION_ENABLED` | false | 기존 규칙 기반 축약도 끄는 전체 스위치. |
| `CONTEXT_COMPACTION_LAYA_ENABLED` | false | Laya 호출 허용 스위치. |
| `CONTEXT_COMPACTION_LAYA_VALIDATED` | false | 같은 평가 사례에서 규칙 기준선보다 나은 결과를 검증하고 승인했음을 운영자가 표시. **테스트 자동 통과 판정이 아니다.** |
| `CONTEXT_COMPACTION_LAYA_TIMEOUT_SECONDS` | 60 | 각 Laya HTTP 요청 제한 시간. |

위 세 스위치와 URL이 모두 설정되어야 Laya 클라이언트를 생성한다. 잘못된 주소를 넣고 모두 켜면 앱 시작에서 오류가 난다. 실제 운영을 켜기 전에는 승인 절차가 필요하다.

오류 상태(400/401/413/422/500/503), 시간 초과, 체크포인트 불일치, 잘못된 응답, 선택지 미포함, 불확실한 선택은 규칙 기반으로 돌아간다. 응답의 확률 0.75 미만을 거르는 것은 **임시 보수적 규칙이며 정확도 보증이나 보정된 확률이 아니다.** 모델 판단을 직접 사용자 답변·비용 원장·권한에 쓰지 않는다.

한 요청에서 Laya 호출은 최대 2회다. 축약 대상 후보가 16줄보다 많거나 순위 후보가 8개보다 많으면 규칙만 쓴다. Laya 서버의 CPU 추론이 짧은 사례에도 오래 걸릴 수 있으므로, 켜기 전 실제 지연과 상위 요청 제한 시간을 측정해야 한다. 서버 거부나 응답 잘림이 의심될 때는 설정만 늘려 해결했다고 주장하지 않는다.

## 실제 서버 읽기 전용 확인

**브리지에서 접근 가능한 Tailscale 노드**에서 다음 명령을 다시 실행해야 한다. 스크린샷의 `<Ubuntu-Tailscale-IP>`는 자리표시자다. 실제 주소는 코드·문서에 넣지 말고 승인된 배포 환경으로만 전달한다.

```sh
LAYA_BASE_URL='http://<실제-Tailscale-주소>:8000' .venv/bin/python -m scripts.check_laya_remote
```

이 스크립트는 `/health`에서 `status=ok`와 `loaded`에 `multilingual`이 있는지 확인하고, 민감 정보가 없는 혼합 언어 문장으로 `/v1/systemone`에 한 번 요청한다. 응답은 실제 `routing.model`과 선택지를 확인한다. 콘솔에는 상태·CPU/GPU 장치 유형·시간만 표시하며 요청 문장이나 원문 응답을 출력하지 않는다. **성공은 접속/프로토콜만 증명하며 축약 품질, 비용 절감, 캐시 적중, 운영 배포 성공은 증명하지 않는다.** 운영 노드에서 명령 실행과 네트워크 변경은 Atlas에 넘긴다.

## 채택 전 평가 기준

실제 대화나 시크릿이 없는 동일 평가 사례를 준비하고, 한국어/영어 혼합·긴 출력·테스트 오류·필수 ID·청구/환불처럼 의미가 중요한 사례를 포함한다. 같은 도구 결과에서 규칙 버전과 Laya 후보를 비교한다.

1. M2: 꼭 남겨야 할 원문 줄이 하나라도 사라지거나 Laya가 원문에 없는 정보를 추가하면 채택하지 않는다. 추가 발췌가 실제로 필요한 정보 발견을 개선하는지 확인한다.
2. M3: 동일 질의에서 필요한 원문 후보의 재발견률과 잘못 상위에 오른 후보를 비교한다. 모든 후보가 목록에 남아 있는지와 최종 복원 주체가 주 LLM인지 확인한다.
3. 각 사례의 Laya 호출 횟수·추가 지연과 상위 모델의 실제 usage(가능한 경우 캐시 읽기/쓰기 포함) 및 성공 작업당 비용을 측정한다. 모의 응답으로 절감률이나 p95를 확정하지 않는다.
4. 400/413/422/503·네트워크 실패·잘못된 체크포인트·저신뢰 응답에서 규칙 경로가 유지되는지 확인한다. 브리지 배포 노드에서 Tailscale ACL과 연결 상태를 확인한다.

**현재 증거:** 개발 머신에서 제공받은 Tailscale 주소로 `/health`는 HTTP 200, `status=ok`, CPU 사용, `multilingual` 적재를 확인했다. 짧은 한국어·영어 혼합 문장을 `/v1/systemone`에 보내 HTTP 200 및 `routing.model=multilingual`을 확인했고, 브리지 `LayaClient.choose()`도 동일한 단일 사례에서 `billing` 선택을 반환했다. 당시 추론 시간은 약 0.2초였다. 로컬 Python 3.13에서 보호 보완 후 자동 테스트는 723개 통과, Starlette 경고 1건이었다. 제한된 동일 사례 비교에서는 한 건의 개선과 한 건의 핵심 정보 누락이 관찰되어 **운영 사용을 보류**했다. 자세한 조건과 수치는 [laya-quality-evaluation.md](laya-quality-evaluation.md)에 기록했다. 개발 머신 결과는 브리지 **배포 노드**의 Tailscale 접근, 실제 대화의 품질, 유료 제공업체 호출 또는 비용 절감을 증명하지 않는다. #19는 Draft·미머지로 유지한다.
