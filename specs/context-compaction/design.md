# 도구 결과 축약·복원 설계 제안

> 상태: **범위 축소 구현 — Laya 미채택, 프로세스 메모리만 사용, 미배포**. 구현 착수용 작업 지시는 [implementation-handoff.md](implementation-handoff.md)를 참조한다. 이 문서는 기존 브리지 설계를 대체하지 않고 `/v1/chat/completions`의 선택적 기능을 다룬다.

## 수용된 범위 축소

2026-09-27에 인증된 소유자·세션·분기 식별자 요구를 낮췄다. 상관 키는 Hermes `session_affinity_header` 코드가 요청에 넣는 `x-hermes-conversation` 값만 사용한다.

- 브리지는 이 값을 만들지 않는다. `user`, 대화 지문, 공유 API 키로 세션을 추정하지 않는다.
- 헤더가 없거나 비어 있으면 축약 상태를 적용하지 않는다.
- 이 값은 인증된 소유자나 분기 ID가 아니다. 위임 트리, `/branch`, 같은 cron 작업, 클라이언트가 직접 넣은 같은 헤더는 한 저장소를 공유한다. 그 한계는 이 범위에 포함된다.
- 저장은 프로세스 메모리와 TTL이다. 재시작이나 Hermes가 원문 메시지를 지운 뒤의 복원은 보장하지 않는다.
- Laya는 같은 사례에서 규칙 기준선보다 나은 결과가 확인되기 전에는 호출하지 않는다. 모델 의존성은 그 확인 없이 추가하지 않는다.

## 목표와 결정

Hermes 클라이언트 코드를 바꾸지 않고, `openai-compatible-bridge`가 **주 LLM에 전달할 과거 도구 결과**를 축약하거나 원문으로 복원한다. Hermes의 원본 대화는 바꾸지 않는다. 압축은 제공업체의 프롬프트 캐시 자체를 만드는 기능이 아니다.

| 책임 | 담당 |
| --- | --- |
| 이미 읽은 결과를 언제, 무엇을 축약할지 최종 결정 | 주 LLM이 브리지 내부 도구 호출 |
| 긴 결과에서 축약본에 남길 원문 구간 선택 | 선택적으로 Laya 같은 System 1 분류 모델. 검증 전 자동 적용 금지 |
| 새 요청과 관련된 축약 결과 중 **unhide 후보를 선정·정렬** | 선택적으로 Laya. 최종 복원 여부는 주 LLM |
| 도구 결과 원문 보관, 축약본 고정, 요청별 가시성 적용, 복원, 권한·비용 검증 | 브리지 |
| 실제 터미널·쿼리 도구 호출 실행 및 원본 대화 유지 | Hermes |

첫 범위는 **과거 `role=tool` 메시지의 긴 결과 본문**이다. 터미널 stdout/stderr, 쿼리 조회 결과, 파일 읽기·검색 결과가 예시다. `assistant.tool_calls`에 담긴 명령어·쿼리문, 사용자 메시지, 주 LLM의 답변은 축약 대상이 아니다. 최신 미소비 결과, 미해결 오류, 필수 식별자·제약·변경 증거는 보호한다. 명령어와 결과 **전체**를 숨기는 기능은 호출/결과 쌍의 유효성을 따로 검증하기 전까지 범위 밖이다.

Palantir AIP Analyst 문서에서 확인되는 것은 숨긴 도구 결과가 후속 모델 호출에 다시 보내지지 않는다는 동작이다.[3] 아래의 **원문 발췌를 남기는 축약본**은 이 프로젝트가 제안하는 별도 설계이며, Palantir의 내부 요청 형식이나 축약 기능이라고 주장하지 않는다.

## 요청 예시 — 도구 결과만 바꾼다

다음은 실제 실행 기록이 아닌 **설명용 가상 예시**다. 주 LLM이 `call_17`의 결과를 읽고 `compact_context(item_42)`를 요청했다고 가정한다.

```json
{"role":"assistant","tool_calls":[{"id":"call_17","type":"function","function":{"name":"terminal","arguments":"{\"command\":\"rg --files src\"}"}}]}
{"role":"tool","tool_call_id":"call_17","content":"src/api.py\nsrc/db.py\n...긴 파일 목록..."}
```

다음 요청에서도 Hermes가 위 원문을 보내더라도, 브리지는 상위 모델로 보내는 **사본**의 결과 본문만 바꾼다.

```json
{"role":"assistant","tool_calls":[{"id":"call_17","type":"function","function":{"name":"terminal","arguments":"{\"command\":\"rg --files src\"}"}}]}
{"role":"tool","tool_call_id":"call_17","content":"[compact:item_42]\n원문 발췌: src/api.py\n원문 발췌: src/db.py\n나머지 결과는 보관됨. 필요하면 unhide_context(item_42)."}
```

명령어가 포함된 호출과 `tool_call_id`는 그대로다. 축약본의 파일명은 Laya가 지어낸 문장이 아니라 저장된 원문의 **정확한 발췌**여야 한다. `unhide_context(item_42)`를 처리하면, 브리지는 저장된 원문으로 전송용 사본을 복구한다. 명령·쿼리를 재실행하지 않는다. 이미 제공업체에 전달한 과거 요청을 소급 삭제하지도 않는다.

## 호출과 저장 경계

```text
Hermes 원본 messages
  -> 브리지: 인증된 세션/분기 식별 + 원본 결과와 호출 ID 매칭
  -> 브리지: 가시성 상태를 조회해 전송용 messages 사본 조립
  -> 제공업체: 주 LLM이 원문 또는 고정된 축약본을 읽음
  -> 내부 compact_context / list_context_items / unhide_context 호출은 브리지가 처리·재호출
  -> Hermes가 실행해야 하는 기존 도구 호출과 최종 답변만 클라이언트에 전달
```

- **내부 도구 이름은 제안이며 아직 API가 아니다.** OpenAI 호환 함수 호출 형태로 브리지가 모델 요청에 주입하고 내부에서 소비한다. MCP 서버와 클라이언트 코드 변경은 범위 밖이다. 클라이언트 도구 이름과 충돌하면 사용하지 않는다.
- 내부 호출에는 도구 결과를 붙여 **제한된 횟수**만 모델을 다시 호출한다. 같은 응답에 내부·외부 도구 호출이 섞이거나 `tool_choice`가 특정 외부 도구로 강제되면 임의로 재배열하지 않는다. 지원 정책을 먼저 테스트로 확정하고, 불안전한 조합에서는 기능을 적용하지 않는다. 기존 외부 도구 호출은 Hermes에 그대로 넘긴다.
- 저장 항목의 논리 키는 인증된 소유자·세션·분기, 도구 호출 ID, 결과 내용 식별자를 결합해야 한다. 원문, 고정 축약본, 원문에서 복사한 구간의 위치, 가시성 버전, 보관·삭제 기한을 관리한다. 동일한 `compact_context` 중복 호출은 같은 결과를 반환한다. 재시도·동시 요청에는 버전 검증이 필요하다.
- **선결 조건:** 현재 확인한 `OpenAIChatRequest`에는 신뢰할 수 있는 동적 세션/분기 ID가 없다(`openai_compatible_bridge/main.py:164-183`). Hermes를 수정하지 않는 조건에서 안전한 전달 방법을 찾지 못하면 다중 세션의 지속 축약·복원을 구현했다고 주장할 수 없다. 임의의 `user` 값이나 대화 지문을 인증 근거로 삼지 않는다. 이 조건이 풀리지 않으면 다음 마일스톤으로 진행하지 않는다.
- Hermes가 자체적으로 과거 메시지를 압축해 원문을 더 이상 보내지 않더라도 복원하려면 영속 저장, 인증된 세션/분기 매칭, 보관 정책이 추가로 필요하다. 원래 `assistant.tool_calls`까지 이력에서 사라졌다면 과거 `role=tool` 메시지만 다시 넣을 수 없으므로, 제공업체가 허용하는 별도의 일반 컨텍스트 또는 유효한 호출/결과 쌍으로 재표현하는 설계·검증도 필요하다. 일시 저장만으로는 재시작·클라이언트 압축 이후 복원을 보장하지 않는다.

현재 접합 지점은 `main.py:1201`의 메시지 정규화 후, `main.py:1267`의 비스트리밍 제공업체 호출 전이다. Foundry OpenAI 경로는 받은 `messages`를 요청 본문에 넣는다(`providers/foundry.py:603-620`). 현재 스트리밍 경로는 도구 호출 delta를 클라이언트로 전달한다(`main.py:1006-1029`). 그래서 첫 구현은 **Foundry OpenAI 프로토콜 + 비스트리밍 + 명시적 opt-in**으로 한정하고, 내부 도구 호출을 스트리밍 중 누출하지 않는 방법은 별도 단계에서 검증한다. Vertex·Ollama·Foundry의 다른 프로토콜은 자동으로 지원된다고 간주하지 않는다.

## 축약본 생성: 규칙 우선, Laya는 선택기

1. 브리지가 도구 결과 유형별로 구조를 확인하고 **반드시 남길 것**(예: 실패 원인, 미해결 오류, 테스트 상태, 필수 ID, 쿼리 결과의 열 이름·행 범위·생략 사실)을 규칙으로 보호한다. 정확한 상태·건수는 파서로 확인할 수 있을 때만 적는다. 불명확하면 원문 유지 또는 명시적 수동 검토로 전환한다.
2. 보호되지 않은 긴 본문을 모델 입력 한도에 맞게 구간으로 나눈다. Laya에는 현재 목표, 도구 유형, 제한된 원문 구간, `남김/검토/제외` 같은 **고정 선택지**만 준다. 긴 전체 대화를 매 요청마다 분류하지 않는다.
3. 브리지가 선택된 원문을 **그대로 복사**해 검증 가능한 축약본을 조립한다. 원문 발췌 위치를 보관한다. Laya가 새로운 요약 문장, 집계 수치, 파일명, 오류 원인을 생성하지 않는다. 모델 실패·잘림·불확실성·검증 실패 시 임의의 축약본을 보내지 않는다.
4. 축약본은 `compact_context` 전환 시 **한 번 생성해 고정**한다. 새 질문마다 본문을 다시 쓰지 않는다. 새 목표에 세부 정보가 필요하면 `unhide_context`로 저장된 원문을 복원한다.

Laya는 생성형 모델이 아니라 typed `choice`/`noul`/`score` 결정을 반환하며, 모델 카드는 기본 1,024토큰 제한, 별도 장문 설정, 과신하는 확률과 특정 typed-decision 벤치마크의 약한 제로샷 성능을 밝힌다.[1] 이 도메인에 대한 성능은 **미검증**이다. Laya 추론과 의존성은 opt-in이며, 먼저 동일한 출력에서 규칙 기반 발췌와 오프라인으로 비교한다. 보호 규칙보다 모델 점수를 우선하지 않는다. 이 기능은 비밀 삭제·접근 제어가 아니다.

## unhide 후보 선정: Laya의 두 번째 역할

새 사용자 요청이 들어오면, 브리지는 **이미 축약된 항목만** 후보로 평가한다. Laya는 요청 내용과 항목 유형·호출 정보·보관된 제한 구간을 비교해 관련성이 높은 항목 ID를 선정·정렬한다. 입력이 너무 길면 구간별로 평가한다. 보정되지 않은 확률을 확정적인 안전 기준으로 사용하지 않는다.

- 주 LLM이 호출할 `list_context_items(query)`의 반환값으로 **짧은 후보 ID·원문 존재 여부·검증된 메타데이터**를 제시하는 방식을 첫 제안으로 한다. Laya가 생성한 자유 형식의 이유를 사실처럼 전달하지 않는다.
- 주 LLM은 목록을 보고 `unhide_context(item_id)`를 호출할 수 있다. **Laya가 자동 unhide를 실행하지 않는다.** 복원되면 해당 원문의 사본을 다음 모델 호출에 포함하되, 도구를 재실행하지 않는다.
- 주 LLM이 목록 도구를 호출하지 않아 필요한 결과를 못 찾는 문제는 평가 대상이다. 필요하다면 최신 요청의 끝에 후보를 알려주는 대안을 검토하되, 이를 초기에 강제하거나 고정 프롬프트 앞부분에 넣지 않는다.
- Laya가 실패하거나 필요한 결과를 후보에서 빠뜨렸을 때도 전체 목록을 조회하고 특정 ID를 복원할 수 있어야 한다. 규칙 기반 검색과 비교해 **필요 증거 재발견율**이 나아지지 않으면 Laya를 채택하지 않는다.

## 프롬프트 캐시와 사용량

```text
원문 상태의 여러 요청 -> compact 전환 -> 첫 축약 요청 -> 축약본 고정 상태의 후속 요청들
                              ↑ 이전 캐시는 이 변경 지점 뒤에서 불일치 가능
                                                   ↑ 새 동일 앞부분은 재사용 가능, 적중 보장 없음
```

OpenAI 문서는 동일한 프롬프트 **앞부분**을 재사용하며, 세션을 유지한다고 항상 적중하지는 않는다고 설명한다.[2] 명령어·호출 ID·초기 지침·내부 도구 선언을 가능한 한 안정적으로 유지한다. 표시 문자열에 시각, 동적 점수, 매번 달라지는 목록을 넣지 않는다. 여러 축약을 같은 전환에 묶을 수 있으나 모델의 명시적 결정과 도구 응답 의미를 깨뜨리면 안 된다. 새 축약·복원, 제공업체 모델/도구 설정 변경, 클라이언트 압축, 캐시 만료 때는 적중률이 달라질 수 있다.

측정 단위는 **실제 제공업체 호출마다** 입력·출력·캐시 읽기/쓰기 토큰(제공업체가 반환할 때), 추가 내부 호출 횟수, 요청 지연, 항목별 원문 대비 축약 길이, 복원 여부, 실패 유형이다. 세션 전체로는 **성공한 작업당 총비용**, 필요한 증거를 놓친 비율, p95 추가 지연을 비교한다. `_coerce_openai_usage`는 제공업체가 캐시 필드를 반환한 경우에만 그 정수를 보존한다. 없는 필드를 0으로 채우거나 모의 응답으로 캐시 적중·절감을 확정하지 않는다. 비용 원장의 정규화 사용량은 기존처럼 입력·출력·합계 토큰이다. 요청 내용·시크릿 원문은 계측 로그에 남기지 않는다.

| 단계 | 완료 기준 / 중단 조건 |
| --- | --- |
| M0. 세션·프로토콜 확인 | 인증된 소유자·분기 ID는 현재 요청으로 확인할 수 없어 범위에서 제외한다. 대신 Hermes가 이미 보내는 `x-hermes-conversation` 원문 값만 상관 키로 사용한다. 헤더가 없거나 Foundry OpenAI 비스트리밍이 아니면 기능을 적용하지 않는다. usage의 캐시 필드는 제공업체가 반환한 경우에만 fixture로 보존한다. |
| M1. 관측과 규칙 기반 기준선 | opt-in 비스트리밍 경로, 원문·축약본 분리, 도구 호출/결과 ID 유지, 내부 도구 라우팅, 항목 저장·만료, 실패 경로 테스트. 실제 호출마다 usage 계상. Laya 없이도 규칙 기반 축약/복원이 동작해야 한다. |
| M2. Laya 축약 선택기 | 긴 `role=tool` 결과에서만 구간 선택. 오류/필수 증거 보호, 장문 분할, 원문 발췌 검증, 모델 실패 시 원문 유지. 규칙 기반과 동일 사례 비교에서 정보 누락·지연·비용을 확인한 후 opt-in 적용. |
| M3. Laya 복원 후보 | 현재 요청과 축약 항목의 관련성 후보를 `list_context_items`로 제공. 주 LLM이 최종 복원. 규칙 기반 검색 대비 재발견율·잘못된 복원·캐시 영향을 비교. |
| M4. 확대 검토 | 비스트리밍 안정화 후 내부/외부 병렬 호출, SSE 버퍼링, 다른 제공업체 프로토콜, 영속 복원 범위를 **각각** 검증해 확대. 자동 unhide나 Laya의 자동 축약 결정은 별도 승인 전까지 제외. |

필수 테스트: 원본 요청 불변, 축약된 `tool.content`만 변경, 호출/결과 ID 정합성, 같은 상태에서 동일한 전송용 과거 메시지 바이트, 중복 호출 멱등성, 복원 원문 동일성, 세션 간 격리·분기/재시도/동시성, 최신 결과·오류 보호, 저장소/Laya 장애 시 안전한 실패, 클라이언트 내부 도구 누출 방지, 모든 상위 호출의 비용 계상. 캐시 **적중**은 모의 응답 테스트로 증명하지 않고, 실제 제공업체 사용량으로 별도 확인한다.

## 미결정 사항

1. 인증된 소유자·세션·분기 식별자는 여전히 없다. 구현 범위는 `x-hermes-conversation` 원문 값으로 낮춰 닫혔다. 그 값은 인증이나 분기 격리를 의미하지 않는다.
2. 도구 이름은 `compact_context`, `list_context_items`, `unhide_context`로 고정한다. 이름이 클라이언트 도구와 겹치거나 `tool_choice`가 특정 함수를 강제하면 기능을 적용하지 않는다. 한 응답에 내부·외부 호출이 섞이면 내부 호출은 실행하지 않고 외부 호출만 원래 순서로 반환한다. `hide_context`와 `[hidden:...]`는 사용하지 않는다.
3. 동적 복원 후보 안내가 필요한 경우, 모델 호출에 어느 위치로 제공해야 기존 캐시 앞부분을 훼손하지 않는가? 첫 제안은 내부 목록 도구 응답이다.
4. 원문 저장 기한, 암호화·접근 제어, 명시적 삭제, Hermes 압축 뒤 복원을 보장할 저장 매체는 별도 승인과 운영 검토가 필요하다.
