# Laya와 규칙 기준선 비교 — 개발 머신의 제한된 평가

## 결론

**운영 Laya 활성화 보류.** 실제 Laya 서버에 비밀·실제 대화가 없는 합성 사례를 보냈다. 초기 M2에서는 규칙이 놓친 한국어 상세 정보 한 건을 추가로 찾았지만, 규칙과 Laya가 함께 중복 청구 핵심 줄 한 건을 놓쳤다. 그 사례는 이후 규칙에서 원문을 유지하도록 보완했다. M3의 단순 사례에서는 기존 규칙이 모두 첫 번째 후보를 맞혀 Laya의 추가 개선이 관찰되지 않았다. 이 결과는 채택 기준을 충족하지 않으며, 전체 도메인 성능을 대표하지 않는다.

## 방법

- 개발 머신의 프로젝트 Python 3.13에서 원격 서버의 `/v1/systemone`을 `LayaClient`로 호출했다. 서버 origin은 저장하지 않는다. 요청은 합성 데이터만 사용했다.
- M2: 각 사례는 규칙이 처음·끝부분을 남길 수 있는 긴 가짜 결과이며 핵심 줄은 중간에 있다. `RuleSpanSelector.select()`가 고른 줄과 `select_extra_lines()`의 제안을 합친 줄을 **같은 사례**에서 비교했다. `refusal_reason`이 발생하지 않는지 확인했다. 핵심 줄 발견 여부와 호출 횟수·단일 요청의 경과 시간을 기록했다.
- M3: `rank_compacted_items()`의 기준 순위와 `rank_items()`의 제안 후 순위를 **같은 질의·세 후보**에서 비교했다. 관련 후보가 첫 번째인지, 후보 목록 전체가 남는지 확인했다.
- 측정 시간은 시험 실행 구간의 벽시계 시간이다. 실제 제공업체 과금, 캐시 재사용, 성공 작업당 비용, p95 지연은 측정하지 않았다.

## 초기 누락 사례 보완 후

`Duplicate invoice INV-EXAMPLE-42 was issued.`와 `중복 청구가 발생했습니다. 확인되지 않은 청구입니다.`를 결과 중간에 넣은 회귀 테스트를 먼저 실행해 둘 다 실패하는 것을 확인했다. 보호 규칙에 해당 문구를 추가한 뒤 두 사례는 축약하지 않고 **원문 전체를 유지**한다. `run_turn()`을 지나는 추가 테스트에서 원문 전송과 원격 Laya 호출 없음도 확인했다. 이는 알려진 형태의 누락을 막지만, 표현이 다른 청구 문제를 모두 검출한다는 뜻은 아니다. 위 시간·선택 결과 표는 **수정 전** 실제 서버 관찰이므로 수정 후 측정값으로 바꾸어 쓰지 않는다.

## 채택 전 미검증 사항

1. 위 중복 청구 표현은 원문 유지로 보완했지만, 다른 표현과 처리 상태(해결됨/미해결)에 대한 포괄적 보호 기준과 회귀 사례가 필요하다. Laya에 안전 판단을 위임하면 안 된다.
2. 더 다양한 한국어·영어 혼합, 긴 출력, 오류, 필수 식별자에 대해 정답 기준을 미리 기록하고 동일 사례의 정보 누락·재발견율을 반복 측정해야 한다.
3. M3은 규칙이 이미 맞는 쉬운 사례만 평가했다. 규칙이 틀리는 합성 사례에서도 Laya의 개선 및 오선택을 비교해야 한다.
4. 실제 상위 모델 응답의 usage·캐시 필드·성공 작업당 비용과 추가 지연을 측정해야 한다. 현재 수치로 비용 절감이나 운영 p95를 주장하지 않는다.
5. 운영 브리지 노드에서 Tailscale 접근 및 Laya의 요청 본문 보존·로그 정책은 Atlas의 운영 점검이 필요하다.

이 문서는 **활성화 거부 판단의 증거**이지 운영 환경의 안전 또는 배포 승인이 아니다. #19는 검토가 끝나더라도 자동 활성화하거나 `main`에 머지하지 않는다.
